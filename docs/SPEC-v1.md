# 有据山寺 · Chinese Fortune Temple 第一版规格

状态：已确认的设计（2026-11-19 设计问答第一至四轮），待建仓库后发为 issue，标签 `ready-for-agent`。

2026-11-20 修订：维护者把整站画风定为暖色丹青插画（GPT Image 套图，见缘起页），入口场景随之改为 **2.5D 插画场景**，不再做 three.js 低多边形 3D。下文与 3D、WebGL 降级有关的条目已按此改写。

## Problem Statement

chinese-fortune 是一套给 AI 编程助手用的 Skill。要用它，得会安装 Claude Code 或 Codex，把 zip 解压进技能目录，再用自然语言提问。这一套对普通人门槛太高：真正想求签、问姻缘、看运势的人，大多不会装 Skill，也不知道它能做什么。

同时，韩国的 Sansa 线上寺庙（2026 年 10 月 26 日上线，一周百万访问）和随后 GitHub 上的一批 three.js 复刻说明，大家愿意在网页里"进一座寺"。这些寺庙只有氛围和仪式（走动、敲木鱼、上香），没有一处能真正算、能查出处。

用户想要的是：打开一个网页就能进寺，不注册、不安装、不付费，通过上香、掷钱、系红绳这样的互动，拿到和 Skill 一样有出处、守边界的结果。

## Solution

做一座以算命为主的网页山寺「有据山寺」。插画场景只当入口：进门 5 秒，小和尚引路，中庭一眼看到五座殿。每座殿的仪式就是 Skill 需要的输入（亲手掷钱就是六爻的六次结果，选两人系红绳就是合婚的两份出生资料）。结果做成「签文卡」：第一层是 Skill 生成的白话首段和一条现实动作，往下展开才是盘面、古籍原文和段号。

浏览器里用 Pyodide 在 Web Worker 中运行 chinese-fortune 原版 Release 包，结果与命令行逐字一致。没有服务器、没有数据库：香客簿（出生资料）和愿望簿只存在本机，可导出、可清除。另有许愿和还愿的仪式，以及从爆款借来的即开即玩、随机法名、敲木鱼、每日一签和分享卡。默认不接大模型；会用 API 密钥的用户可以在设置里填自己的密钥做追问，模型的回答必须先通过 Skill 的 `answer_check`。

## User Stories

进门与引导

1. 作为第一次来的访客，我想打开网页 5 秒内就进寺，不用注册，这样我愿意试一试。
2. 作为访客，我想进门时得到一个随机法名（例如「闲云」「静月」），这样有被接待的感觉，也方便分享。
3. 作为访客，我想有一个小和尚引路，告诉我五座殿各能做什么，这样我不用读说明。
4. 作为手机用户，我想点一下地面或殿门就能走过去，不用操作方向键。
5. 作为急着求签的访客，我想从打开网页到拿到第一支签不超过 60 秒。
6. 作为访客，我想在中庭一眼看到求签殿、月老殿、黄历亭、问心堂、紫微殿和许愿树，这样我知道去哪里。
7. 作为第一次加载的访客，我想在算法包加载的十几秒里敲木鱼、拨念珠，听钟声，这样等待不无聊。
8. 作为访客，我想看到算法包加载的进度和"完成后可以离线使用"的提示，这样我知道为什么第一次要等。
9. 作为第二次来的访客，我想几乎立刻进寺，并且断网时也能算。
10. 作为说英语的访客，我想切换到英文界面，签文和古籍原文仍保留中文，旁边附白话。

香客簿（出生资料）

11. 作为香客，我想只录一次出生资料，以后各殿直接选，不用重复填写。
12. 作为香客，我想在香客簿里存几个人（自己、伴侣、家人），并给他们起称呼。
13. 作为不知道出生时辰的香客，我想勾选"时辰不知道"，结果只说能确定的部分。
14. 作为香客，我想从城市列表里选出生地，经度和时区自动带出。
15. 作为香客，我想只写日期时默认按公历算，并在结果里看到"按公历算"一句；要用农历时我可以明确切换。
16. 作为香客，我想在需要"现在"的殿里，确认一次浏览器推测的时区，而不是被默默当成我所在的时区。
17. 作为注重隐私的香客，我想知道资料只存在本机，并能一键导出成文件、一键全部清除。
18. 作为换设备的香客，我想导入之前导出的文件，恢复香客簿和愿望簿。

求签殿（六爻）

19. 作为求签的人，我想亲手掷三枚铜钱六次，每一次的结果就是一爻，这样我知道签是我自己摇出来的。
20. 作为求签的人，我想从预设里选所问之事（面试、考试、感情、押金等），或者自己写一句。
21. 作为求签的人，我想先看到卦名、动爻、成败有没有断，以及一条现实跟进动作。
22. 作为想深究的人，我想展开看到装卦表、用神、日月生克和古籍原文，每个段号都能点开看原文。
23. 作为问面试的人，我想不被告知"一定能过"或"一定不过"，也不被推定通知日期。

月老殿（合婚）

24. 作为问姻缘的人，我想从香客簿选两个人，在殿前系红绳，看两人八字之间的合、冲、刑、害。
25. 作为问姻缘的人，我想看到三元九宫合婚的起宫、步数和合成结果，以及《协纪辨方书》对此法的驳议。
26. 作为点名要按《协纪辨方书》算的人，我想看到按那本书起宫的结果。
27. 作为问姻缘的人，我想不看到婚配分数，也不被告知"一定会分手"或"一定能结婚"。
28. 作为只知道两人生日、不知道时辰的人，我也想看到能算的部分（年柱、三元合婚）。

黄历亭（运势与择日）

29. 作为想知道今天怎么样的人，我想看到今日按出生年借用相主的等级，并知道这是传统择日等级，不是对我生活的预测。
30. 作为想安排一周的人，我想看到本周每天的等级和理由，并知道同级的几天不分先后。
31. 作为想搬家的人，我想问某个月哪几天好，先看到整月的日干支、建除、原文忌日和冲生年的日子，再选办事城市。
32. 作为问"最近事业怎么样"的人，我想先看到已判、未判和一条现实动作，只有我问哪天时才展开择日等级。
33. 作为香客，我想看到交节时刻只说到分钟，并知道交节前后的月份不同。

问心堂（人生建议）

34. 作为有现实烦恼的人，我想写下心事，得到《高性价比人生指南》里对应的现实建议。
35. 作为遇到紧急情况的人（胸痛、燃气泄漏、想伤害自己），我想第一时间看到该做的第一步和求助方式，而不是算命。
36. 作为问法律、医疗、投资问题的人，我想被告知这里不做裁决，并被引导到现实帮助。

紫微殿

37. 作为想了解自己适合什么工作的人，我想选"事业"主题，看到官禄宫盘面一句、哪些原文条件本盘不成立、以及一条现实工作动作。
38. 作为闰月出生的人，我想看到两种闰月取法各自的盘，而不是只看到一种。
39. 作为想看感情或财运的人，我想选对应主题，看到相应宫位的盘面和原句。
40. 作为不懂紫微的人，我想看到对宫、三合、亮度、四化这些词的白话解释。

签文卡与分享

41. 作为香客，我想每次的结果都是一张签文卡，第一段就能读懂结论。
42. 作为香客，我想边界说明（文化参考、不预测健康寿命等）在整趟游戏里只看到一次，不在每张卡上重复。
43. 作为想分享的人，我想一键生成分享图，默认隐去出生日期、时辰和四柱。
44. 作为香客，我想看到每张卡对应的 Skill 版本，方便和命令行结果对照。

许愿与还愿

45. 作为香客，我想在许愿树下写一个心愿，选类别和回来还愿的日子。
46. 作为刚求完签的人，我想在签文卡底部"就此事许个愿"，愿望会记下它来自哪支签。
47. 作为许愿的人，我想自己选还愿的日子，而不是由卦象或择日结果自动定。
48. 作为许愿的人，我想下载一个日历文件，把还愿提醒放进手机日历。
49. 作为回访的香客，我想在进门时被提醒"你在某月许的愿到期了"。
50. 作为愿望达成的人，我想回来上香、点灯或在许愿树上挂红绸，完成还愿。
51. 作为愿望没实现的人，我想可以选择"放下"，并且不被告知这是失败或会招灾。
52. 作为祈求家人健康的人，我想能许这个愿，同时看到"身体不适先就医"。
53. 作为香客，我想在愿望簿里看到每一条的状态：已许、已还、已放下。
54. 作为香客，我想愿望原文只存在本机，分享卡默认只显示类别、日期和"已还愿"。
55. 作为想许伤害他人之愿的人，我会被温和地拒绝，并看到原因。
56. 作为香客，我想每次还愿记一笔功德，只作个人记录，不排名、不兑换。
57. 作为香客，我想看到还愿卡上写着"这是仪式，不是推算"，不被误导为有古籍依据。

爆款借鉴

58. 作为每天来的香客，我想有"每日一签"，并能分享出去。
59. 作为想静心的访客，我想不求签也能敲木鱼、拨 108 颗念珠、合掌礼拜。
60. 作为访客，我想听到钟声、诵经和风声，并能一键静音。

大模型追问（可选）

61. 作为有 API 密钥的高级用户，我想在设置里填自己的 Anthropic 或 OpenAI 兼容接口密钥，对签文卡追问。
62. 作为高级用户，我想密钥只存在本机，随时可删除。
63. 作为高级用户，我想模型只根据本次 Skill 的工具结果回答，并在回答显示前通过 `answer_check`；不通过的回答不显示，并告诉我原因。
64. 作为订阅了 Claude 或 ChatGPT 的用户，我想看到一页说明：网页里不能用订阅登录，但可以在 Claude Code 或 Codex 里装 Skill。

设备、署名与统计

65. 作为用老手机的访客，我想入口场景不依赖 WebGL，五座殿和许愿树在任何手机上都能用。
66. 作为中端手机用户，我想入口场景的动画流畅，并能在系统里关掉动画。
67. 作为好奇来源的访客，我想在「缘起」页看到 Skill、古籍转录、书文和开源库的出处与许可证。
68. 作为维护者，我想看到不用 Cookie、不含个人数据的访问统计，知道有没有人来、从哪里来。
69. 作为维护者，我想 Skill 发新版时只改一个版本号，CI 验证通过后再上线。

## Implementation Decisions

**仓库与依赖**

- 新建独立仓库 `chinese-fortune-temple`（中文名「有据山寺」，英文名 Chinese Fortune Temple），MIT 许可。chinese-fortune 仓库不做任何改动。
- Skill 以 Release 包接入：构建时按配置里的版本号（第一版为 v6.3.0）下载 `chinese-fortune-vX.Y.Z.zip`、`SHA256SUMS`、`CI-PROVENANCE.json`，校验哈希和来源提交后再打进站点。版本号是唯一的升级入口。不用 git submodule，不复制 Skill 源码。
- 技术栈：Vite、TypeScript，不用 React，也不用 three.js；Pyodide 放在 Web Worker 里；Service Worker 缓存站点、Pyodide 和 Skill 包。

**模块**（每个模块对外的接口尽量窄）

- **Skill 运行器（Worker）**：在 Pyodide 中解开 Skill 运行包，把 `scripts` 和随包的 `vendor.zip` 放进模块搜索路径，对外只有一个接口：

  ```ts
  // 设计决定（非实现）：与命令行同构，便于逐字比对
  type ToolCall = { script: string; argv: string[]; stdin?: string };
  type ToolResult = { exitCode: number; stdout: string; json?: unknown };
  runTool(call: ToolCall): Promise<ToolResult>;
  ```

  内部调用各脚本的 `main(argv)`，替换标准输入输出。"现在"由主线程传入（`--request-time` 用 UTC 时刻，`--current-timezone` 用用户确认过的时区），Worker 不自行读取时钟或时区。加载分阶段上报进度。
- **殿（Hall）**：每座殿把仪式输入转成一次或几次 `ToolCall`，再把结果交给签文卡。对应关系：
  - 求签殿：`liuyao_cast.py coins --lines <六次结果> --date --time --target-timezone --question`；使用 `first_answer` 作为首段。
  - 月老殿：`pair_facts.py --stdin`，传入两人出生资料和原话（原话点名《协纪辨方书》时走该书起宫）。
  - 黄历亭：`fortune_reading.py --stdin`（今日、本周、最近）；问某月哪天时用 `huangli_query.py --month`。
  - 问心堂：先 `question_router.py --question` 分流；急症或自伤先走 life-guide 的安全路径；其余用 `life_guide.py`。
  - 紫微殿：`ziwei_calc.py --focus-palace <主题>`；首段用 `focus.career.first_answer` 或对应宫位的 `say`、`terms`、`condition_charts`。
- **签文卡**：输入一次殿的工具结果，输出三层：第一层是工具给的白话首段和现实动作（不再加工改写）；第二层是盘面表；第三层是原文和段号（点开用 `classical_search.py --passage-id` 取原文）。卡上注明 Skill 版本。显示前对卡片正文跑 `answer_check.py --stdin`，结果为 error 时不显示，并说明原因。
- **香客簿**：本机存储（IndexedDB，带版本号的结构，支持迁移），存多人出生资料、称呼、时辰是否已知、城市（经度和时区来自 Skill 的城市表）、历法（默认公历）。导出与导入为一个 JSON 文件；一键清除。
- **愿望簿**：本机存储，记录类别、原文、来源签（可空）、还愿日、状态（已许、已还、已放下）、功德记录。到期提醒在进门时显示；可生成 `.ics` 日历文件。拒收伤害他人的愿望（关键词和规则判断，在本机完成）。
- **寺院场景**：2.5D 插画场景，用中庭全景插画当地图，每座殿的匾额钉在画上对应位置；点哪座殿，小和尚从山门走过去再进殿（减少动画时直接进）；殿格列表保留给键盘、读屏和小屏。禅台有木鱼、念珠、钟、合掌和环境声（风声、诵经），声音由浏览器合成。
- **分享卡**：在本机用 canvas 生成图片，默认隐去出生资料；愿望原文默认不显示。
- **追问（可选）**：用户自带密钥，支持 Anthropic（浏览器直连）与 OpenAI 兼容接口；密钥只存在本机；发送给模型的只有本次工具输出和 SKILL.md 规则；回答显示前过 `answer_check`。另有一页说明订阅会员不能在网页里使用，引导到 Claude Code 或 Codex 安装 Skill。
- **国际化**：中文首发，界面同时做英文；签文、古籍原文保留中文并附白话。
- **托管与统计**：Cloudflare Pages（先用 `pages.dev`，以后再绑自有域名），GitHub Actions 构建；Cloudflare Web Analytics，不用 Cookie、不采集个人数据。
- **署名**：「缘起」页列出 Skill（MIT）、随包古籍及各自授权（从算法包读出）、life-guide 书文（CC BY 4.0）、Pyodide 和 Skill 打包的运行库，以及插画与声音的来源。

**边界**（沿用 Skill，不新增推断）

- 不做健康、死亡断语，不做投资或法律裁决，不做婚配分数，不打包票。
- 边界说明在整趟游戏里只说一次。
- 还愿不承诺灵验，不写"不还愿会招灾"；还愿卡写明"这是仪式，不是推算"，不配古籍出处。
- 还愿日由用户自选，不从应期或择日等级推出。
- 第一版不商用：无打赏、广告、付费解签。

## Testing Decisions

- 好的测试只看外部行为：用户能看到的卡片、能完成的流程、本机存下的数据，以及工具的输出。不对内部函数单独写测试。
- **主接口：端到端（Playwright，对构建好的站点）**，全部使用虚构出生资料，至少覆盖：
  - 进门、随机法名、引路，从打开到第一支签的时间；
  - 求签殿：固定的六次掷钱结果得到预期卦名和首段；
  - 月老殿：两人合婚，有三元合婚结果、无婚配分数；点名《协纪辨方书》时起宫不同；
  - 黄历亭：本周等级；某月整月列表含冲生年的日子；
  - 问心堂：普通问题得到建议；急症、自伤问题先给第一步；
  - 紫微殿：事业主题含未判与工作动作；闰月出生显示两种盘；
  - 许愿、到期提醒、还愿、放下；拒收伤害他人的愿望；
  - 香客簿和愿望簿的导出、导入、清除；分享图默认不含出生资料；
  - 入口场景点殿进殿，减少动画时直接进殿；
  - 断网后再次打开仍能算。
- **一致性接口：Worker 与命令行逐字比对**。对每座殿的典型输入，用同一版本 Skill 在 Python 命令行跑一遍，把输出存为参照；Worker 里 `runTool` 的输出必须逐字相同（时间相关的输入固定为同一参考时刻）。Skill 升版时，这组参照随之重生成。
- 参考做法：chinese-fortune 仓库的锁定测试（如 `tests/test_round11_fixes.py`）用虚构资料和独立历算做期望值；本仓库沿用"期望值来自独立来源或 Skill 命令行，不在测试里重算"的原则。
- CI：每次提交跑端到端和一致性测试；Skill 版本号变更时必须全绿才能发布。

## Out of Scope

- 同屏香客、实时互动、排行榜、功德换装。
- 服务器、数据库、账号体系、跨设备同步（只提供文件导出导入）。
- 订阅会员登录（Claude、ChatGPT 订阅都不能在第三方网页使用）。
- fortune-extras（塔罗、星座、解梦）、风水、起名、梅花易数等第二版候选。
- ChatGPT 应用、Claude 连接器。
- 商用：打赏、广告、付费功能。
- 自有域名（先用 `pages.dev`）。

## Further Notes

**为什么这样做的依据**

- Sansa：2026 年 10 月 26 日上线，不到一周超过 100 万访问；无注册、随机法名、小和尚形象、敲木鱼与念珠、没有聊天。GitHub 上的复刻（静寺、山寺、云隐寺、财神庙、云上禅境）都没有可核出处的算法。静寺声明其前端版权归 Sansa 原作者，本项目不使用其代码或素材。
- Skill v6.3.0 运行包解压后约 8.6MB，纯 Python，依赖只有随包的 lunar_python 和 tzdata，没有原生扩展，可在 Pyodide 中运行；第一次加载（Pyodide 加 Skill）约 15–20MB，需后台加载并缓存。
- Vercel 免费版只允许非商用、每月流量 100GB 且不能加购；Cloudflare Pages 免费版不限流量，适合可能突然爆火的静态站。
- `*.pages.dev` 在中国大陆访问可能不稳定；正式推广前需要绑自有域名。

**建议的实施顺序**（每一步都能独立演示，每一步完成后跑测试）

1. 仓库骨架与 CI：Vite、TypeScript、Playwright；按版本号下载并校验 Skill 包。
2. Skill 运行器（Worker）与一致性测试：先打通一个工具（`liuyao_cast`），再覆盖五座殿用到的全部工具。
3. 2D 水墨版的五座殿与签文卡（先不做 3D），香客簿和愿望簿的本机存储、导出导入清除。端到端测试从这一步开始覆盖主要流程。
4. 许愿与还愿、到期提醒、`.ics`、分享卡。
5. 2.5D 寺院场景：中庭插画上的五座殿与许愿树、小和尚引路、点击寻路、木鱼念珠、音效；加载期间的互动；每日一签。
6. 英文界面、「缘起」页、可选的自带密钥追问。
7. Cloudflare Pages 部署、Web Analytics、离线缓存验证；首发。

先做殿和卡再做入口场景，是因为算命为主：殿和卡的逻辑先跑通，场景只是外壳。
